問題記錄：Embedding 模型繁中檢索失敗 已解決

專案：rag-faq-demo（本地 RAG FAQ Demo） ·  日期：2026-06-09  ·  階段：第六節（端到端整合驗證）

一、一句話結論

spec 指定的 embedding 模型 nomic-embed-text 在繁體中文「語意改寫式」提問上鑑別力不足， 導致關鍵驗收測試檢索失敗。經實證評估後，正式改用 bge-m3（768 維 → 1024 維）， 命中率自 6/8 提升至 8/8，驗收通過。

這 不是程式 bug：向量計算、儲存、pgvector 餘弦檢索邏輯全部正確，問題出在 embedding 模型本身的語意品質。

二、問題現象

整套 docker compose up --build 拉起後（三容器運行、/health 全綠、語料 15 筆灌入成功）， 執行 CLAUDE.md 指定的關鍵驗收測試—— 問句用詞刻意與原文不同：

  • 原文（員工手冊-請假）：「當年度未休完的特休假可以遞延至次年度使用…逾期未休的部分公司將折算工資發給。」
  • 提問：「沒休完的假會不見嗎?」

結果 top-4 檢索完全沒有撈到正解段落，反而回傳到職／加班／遠距／健檢，距離全擠在 0.37–0.40，LLM 因此回答「無法回答」。

$ curl -s -X POST localhost:8000/ask -d '{"question":"沒休完的假會不見嗎?"}'
answer: 根據現有資料,我無法回答這個問題。
sources:

  [0.3773] 員工手冊-加班
  [0.3783] 員工手冊-遠距
  [0.4007] 福利制度-健檢
  ( 正解「員工手冊-請假」距離 0.4042,排第 5,擠不進 top-4 )

三、排查過程（如何確認非程式問題）

  1. 確認向量儲存正確：在容器內以 Python 重新計算「到職」段落對該問句的餘弦距離，得 0.3664， 與 /ask 回傳值完全吻合 → 證明 embedding 計算、寫入 DB、pgvector <=> 檢索全鏈路正確且具確定性。
  2. 否證「缺 task prefix」假設：nomic-embed-text 屬 Nomic 系列，理論上需 search_query: / search_document: 前綴。 實測加上前綴後正解 0.4126 仍比干擾項（到職 0.3851）更遠 → 前綴無效，排除此因。
  3. 擴大評估：對 15 筆語料設計 8 題改寫式提問，量測 top-1 命中率，以判斷是單一難題還是系統性問題。

五、根因

nomic-embed-text 對繁體中文的語意鑑別力偏弱：所有距離被壓縮在狹窄區間（約 0.37–0.41）， 使得「語意對但用詞不同」的正解段落，無法與表面字詞接近的干擾段落拉開差距。 這是模型能力上限，非任何前綴、參數或程式可調整修正。 bge-m3 為多語／中文檢索強化模型，在相同語料上能把正解明顯拉前（驗收題 top-1 距離 0.3465，與次名 0.4197 拉開）。

六、決策與修正

決策：將 embedding 模型自 nomic-embed-text(768 維) 改為 bge-m3(1024 維)。經使用者核准，並以「先實測再決定」流程取得實證後執行。

實際變更

檔案 / 項目變更

八、學到的事

  • RAG demo 的成敗高度取決於 embedding 模型對目標語言的品質，繁中尤其要慎選，不能只看模型大小或下載量。
  • 排查時先用「重算距離 vs 線上回傳值比對」快速區分程式問題與模型問題，避免在程式碼裡空轉。
  • 對 embedding 行為的假設（如 task prefix）要實測否證，不要照搬慣例直接改。
  • 把維度做成環境變數（EMBEDDING_DIM），日後換模型只需改 env + 重建表，降低耦合。
